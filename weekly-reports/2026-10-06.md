# Weekly check — 6 Oct 2026 (the first one)

The check was switched on this day, right after the repository went public.
It ran twice: once when it was set up, and once more by hand. Both reports
are kept below as they arrived; the second confirms the first.

## Report (first run)

Verdict: Something needs a look

**Tests:** all 127 automated tests pass, 0 fail. The installation (`npm ci`) worked normally.

**Dependencies**

- **Security warnings ("advisories"):** there are no new ones. `npm audit` lists 25 findings (18 high, 7 moderate), all from the four known, accepted issues: braces/micromatch, node-forge, uuid and source-map-js. Each one sits only inside Expo's build tools on your Mac (under `@expo/cli`, `@expo/metro-config` and `@expo/config-plugins`), so none of them ends up in the app. The docs still say "24 / 17 high" because source-map-js was added on 6 Oct; the advisory isn't new.
- **Newer versions:**
  - `expo` 57.0.27 (yours: 57.0.26), released today. Its changelog says "no user-facing changes", with no security fix. It only moves Expo's helper packages up by one small version.
  - `expo-screen-capture` 57.0.4 (yours: 57.0.3), released today. It fixes two bugs that only affect iPhones, with no security fix and no effect on Android. You don't need to update it urgently.
  - `@noble/*` and `@scure/*` 2.x, and `@noble/ed25519` 3.x: these are the newer major versions you're already skipping on purpose (DEPENDENCIES.md, finding 5). No newer 1.x versions exist.
  - Everything else is up to date: the Klever libraries, `react-native-quick-crypto`, `expo-secure-store` and `expo-crypto`.

**Code changes and review**

The whole project is less than 8 days old, so this first check reviewed all of the code, including the example app. Four separate reviewers each took one area. I checked the most important finding against the code myself.

- **Medium (app-to-app):** a request can be passed through so that it appears to come from an app you already allowed. Here is how: a trusted app (for example the Hub) opens another app, say a photo picker. If that other app is harmful, it can hand a signing request on to the Signer, and Android then names the trusted app as the sender. The Signer would skip "Allow this app?", show the trusted app's name on the approval screen, and give out your address without asking. The harmful app never receives the signature, which limits the damage, but it contradicts SECURITY.md's "Fake client app: Protected". The fix is small: refuse any request that carries Android's "forward result" flag (SignRequestActivity.kt, line 62). Real client apps never use that flag.
- **Low (passwords):** the weak-password filter still accepts close variants of common passwords, such as "Passw0rd1234", "passwordpassword" and "qwertyqwerty".
- **Low (password lock):** when the key is locked again with a new or upgraded password, the new lock isn't test-opened before the old one is replaced. This is unlikely to go wrong, but if it did, you would need your recovery words.
- **Low (notes):** a few rare right-to-left alphabets and invisible characters still get through in an app's note. They can make the words show in a different order than they were written. The note stays inside the "written by the app, not checked" box.
- **Low (app names):** an app's name can still mix text directions or contain blank-looking characters. The app id shown underneath stays correct.
- **Low (signing history):** if the saved history of recent signatures were damaged, the "same transfer again" and "many requests quickly" warnings would quietly switch off instead of failing safe. That needs damaged storage to happen.
- **Low (release check):** the check before publishing doesn't look for other ways into the app that a library might add, or for the Android 12 minimum.
- **Low (example app):** the example sends the transaction the server prepared without first checking it against what the user typed. The Signer's own approval screen is still the real protection.

The transaction reviewer found no way to make the Signer sign something other than what it shows. That included 200,000 deliberately damaged test transactions, with 0 mismatches. The crypto review found the vault, the randomness, the wrong-password waits and the fingerprint flow sound.

**Docs vs code:** every protection the docs promise is really in the code. Some numbers and wording are out of date:

- README says "117 checks"; there are 127.
- The audit counts are out of date (see above).
- "The password always works too" isn't true while a risky accessibility app is switched on. In that case, signing with the password is blocked.
- Notes with direction-changing characters aren't refused, as SECURITY.md says. The Signer shows them as unreadable data instead.
- README doesn't mention the third review.

**Anything else:** the 0.1.0 release checksum on GitHub matches `released-versions.json`. I couldn't use GitHub's API, so I downloaded the checksum file directly from the v0.1.0 release. Nothing in the repository was changed.

## What became of it

All points were fixed on 6 Oct 2026 and released in 0.1.1:

- Medium, requests passed on by another app: refused since 6 Oct (commit
  fadab94). Seen refused on a phone on 19 Oct (TESTING.md F30).
- Low, password variants ("Passw0rd1234", "qwertyqwerty"): refused (70592b1).
- Low, password lock not test-opened: new locks are test-opened before they
  replace the old one (70592b1).
- Low, notes and app names (right-to-left scripts, invisible marks, mixed
  directions): handled (70592b1).
- Low, damaged signing history: asks for the extra confirmation (70592b1;
  extended to one hour on 19 Oct after the 12 Oct check).
- Low, release check: also requires Android 12+ and no extra open entry
  points (70592b1; made stricter on 19 Oct after the 12 Oct check).
- Low, example app: checks what the node prepared (70592b1; its comments
  were made honest on 19 Oct after the 12 Oct check).
- Docs: test count, audit counts, "the password always works too", notes
  wording, third review in the README: corrected (fadab94, efbdbc3).
