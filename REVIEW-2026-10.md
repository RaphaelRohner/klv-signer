# REVIEW-2026-10.md — second review of the KLV Signer (1 Oct 2026)

> **What this is:** an AI review, not a professional audit. It was done by
> Claude (Anthropic), the same AI that helped write the code, using four
> separate review passes that each looked at one part of the app without
> seeing the others' results. It finds a lot, but it can miss things a human
> expert would catch, and it shares blind spots with the code's author.
> Feedback from anyone who reads the code is very welcome (see "Reporting a
> vulnerability" in [SECURITY.md](SECURITY.md)).

**Version reviewed:** the repository as of commit `ede8992` (end of the
Stage 4 safety work), testnet only.

## Summary

- **No way was found to make the Signer sign something other than what it
  shows, to read the key, or to sign without the user's password or
  fingerprint.**
- 31 smaller problems were found and **fixed** in this round (listed
  below). Most are about rare timing cases, text that could look misleading,
  and checks that should fail safe.
- 13 items are **still open** (listed at the end): none is a known way to
  steal funds, but each would make the Signer a little stronger.
- After the fixes: 103 automatic tests pass (92 before the review; 11 new
  ones cover the fixes), and the phone tests in TESTING.md (part F13) cover
  the visible changes.

**Found during the phone tests afterwards (1 Oct 2026):** some yellow
message boxes, including the "try again in …" countdown after wrong
passwords and "This transaction contains N transfers", showed no text at
all, because Android only draws text that sits inside a text element. Fixed.
All phone tests for this round (TESTING.md, F13) passed.

**Found during the new-look phone tests (1 Oct 2026):** with "Show" on,
the keyboard (Gboard) learned the app password and later offered it as a
suggestion, and Google's password manager offered to save it (once even
pairing it with the amount box as "username"). Fixed in layers: password
boxes always stay password boxes ("Show" displays the text underneath),
autofill is off for every box and the whole window, and any autofill session
is ended on every keystroke, focus and screen change. Lesson for testers:
check keyboard suggestions and "Save password?" prompts on every screen with
a password box.

## How it was reviewed

| Pass | What it covered | How |
| --- | --- | --- |
| 1. Keys and storage | Wallet creation, the password vault (scrypt + AES-GCM), fingerprint/face copy, wrong-password waits, removing the wallet | Reading every line; thinking through crashes and timing between steps |
| 2. The transaction reader | `readTransaction.js`, `format.js`, the protobuf reader | Reading every line, plus **500,000 randomly damaged transactions** (fuzzing) checking the reader never crashes, never accepts something it can't re-create byte for byte, and never shows misleading text |
| 3. Android and app-to-app requests | The Kotlin "front door", the manifest, permissions, phone-safety checks, window protection | Reading every line; Android's documented behaviour for each setting |
| 4. Screens and flows | Every screen in `App.js` and `src/screens/`: what happens when you leave, a new request arrives, or a slow step finishes late | Walking through each path, especially "what if two things happen at once" |

## Fixed in this round

Severity: **Medium** = could mislead the user or weaken a protection in a
realistic case; **Low** = rare, or only makes an attack slightly easier.

### What you see before signing

| # | Severity | Problem | Fix |
| --- | --- | --- | --- |
| 1 | Medium | A token name or network ID could start with an invisible character (a "byte order mark"), so a different token could be displayed exactly like `KLV`. | Token names must now be plain capital letters and digits in Klever's format (`KLV`, `KFI`, `ABC-1A2B`, NFTs `ABC-1A2B/123`), checked on the raw bytes before they're turned into text. The network ID must be plain digits. |
| 2 | Medium | An attached note (text written by the app) could contain line breaks, direction-changing or invisible characters, and so imitate the Signer's own text on the approval screen. | Notes are shown only if every character is an ordinary letter, digit, punctuation mark or symbol, at most 256 characters; otherwise "data the Signer can't show as text (N bytes)". Notes now sit in a dashed box labelled **"written by the app, not checked"**. |
| 3 | Low | No limit on the number of notes, or on the fee. | More than 5 notes, or a fee over 100 KLV, are refused (real Klever fees are tiny). |
| 4 | Low | A huge input was converted before its size was checked. | The size is checked first. |
| 5 | Low | The network fee didn't count towards the "Large amounts" setting. | It does now (when something goes to a receiver that isn't trusted); the message says "(network fee included)". |
| 6 | Low | Tokens other than KLV can't always be shown in whole tokens (unknown decimal places), but the "Other tokens" rule was off by default. | On by default for new installs. Existing settings are kept. |
| 7 | Low | Long receiver addresses are hard to compare. | Shown in groups of 4 characters. |

### Requests from other apps

| # | Severity | Problem | Fix |
| --- | --- | --- | --- |
| 8 | Medium | In rare timing cases (a new request arriving while a password check was still running), an answer could be sent for a different request than the one on screen. | Every answer is tied to the request it was made for and is dropped if that request is gone. Slow steps that finish after you left are ignored ("sessions"). |
| 9 | Medium | A request arriving while you were approving a pasted transaction could crash the Signer. | Fixed with the same session mechanism. |
| 10 | Low | An app you hadn't allowed could learn whether a wallet is set up (`NO_WALLET`). | Unknown apps get "Allow this app?" first; `NO_WALLET` only after that. |
| 11 | Low | If an allowed app was later re-signed with a different certificate (e.g. replaced by a fake), the Signer relied on a single stored fingerprint check. | Uses Android's own `hasSigningCertificate` check, which also handles certificate rotation correctly. |
| 12 | Low | App names come from the asking app and could contain invisible characters or be very long. | Cleaned and shortened to 40 characters ("(no name)" if nothing is left). |
| 13 | Low | Unusual extras in a request could crash the front door. | Caught; the app gets `INVALID_REQUEST`. |
| 14 | Low | The Signer had a public "intent filter", so it could be found by its request types and other apps could declare the same ones. | Removed. The Signer can only be called by its exact name (SIGNER-PROTOCOL.md 2b). |
| 15 | Low | A signature was remembered as "sent to this receiver" even when it never reached the app. | Only remembered after the answer was delivered. |

### Password, fingerprint and waiting times

| # | Severity | Problem | Fix |
| --- | --- | --- | --- |
| 16 | Medium | Wrong-password waits used the phone's clock: moving the clock forward skipped the wait. | Waits are timed with Android's stopwatch since the phone started, which the clock setting doesn't affect. After a restart a running wait starts again. Moving the clock back can't make a wait longer either. |
| 17 | Medium | Closing the Signer in the middle of a password check meant the wrong guess was never counted. | Each try is counted as wrong **before** it's checked, and undone if it was right. |
| 18 | Medium | Two screens could run password checks at the same time, so several guesses counted as one. | One check at a time across the whole app. |
| 19 | Low | With "Show" on, a password was typed with the normal keyboard, which may learn visible text. | First fixed by switching the keyboard's suggestions off while shown; the phone tests showed some keyboards and autofill still reacted. Final fix (1 Oct 2026): the password box always stays a password box, and "Show" displays what you typed underneath instead. |
| 20 | Low | The fast password engine's startup self-check used settings far lighter than the real ones. | It now uses the same structure as the real settings (r = 8). |

### Safety checks failing safe

| # | Severity | Problem | Fix |
| --- | --- | --- | --- |
| 21 | Medium | If the phone-safety check itself failed, signing stayed on. | Signing is off until the check runs ("The phone-safety check couldn't run"). Apps get `UNSAFE_DEVICE`. |
| 22 | Low | A system query in the phone check could hang. | Stopped after 2 seconds. |
| 23 | Low | If the extra-confirmation settings couldn't be read, the extra confirmation was asked without the wait you may have chosen. | The longest wait (30 s) is used then. |

### Storage and setup

| # | Severity | Problem | Fix |
| --- | --- | --- | --- |
| 24 | Medium | If the phone's storage returned an error or only half a wallet, the Signer could behave as if there were no wallet, inviting you to overwrite it. | New "storage problem" screen that explains the situation; nothing is overwritten. |
| 25 | Medium | Setting up a new wallet could overwrite an existing one in a rare timing case. | Saving a new wallet refuses if one already exists. |
| 26 | Low | The order of saving could leave a wallet without its address after a crash. | The vault is now written last, so a half-saved wallet is detected. |
| 27 | Low | Leaving the Signer during setup kept the new recovery words in memory and on screen. | Leaving during setup goes back to the start and drops the words. |
| 28 | Low | Back on the approval screen during a slow step could let it finish later. | Ends the session; nothing happens afterwards. |

### Permissions and small things

| # | Severity | Problem | Fix |
| --- | --- | --- | --- |
| 29 | Low | Two photo/video permissions could be added by a library. | Blocked, and the automatic test checks it. |
| 30 | Low | Screen readers (TalkBack) didn't announce errors or the state of buttons. | Text boxes, buttons and messages are labelled; errors are read out when they appear. |
| 31 | Low | The address-ending check was described as protection against look-alike addresses. | Re-worded: typing the ending makes you **look** at the address; a look-alike can have the same ending, so compare all of it. |

## Still open

| Item | Why it's still open |
| --- | --- |
| Client apps can't yet verify the Signer | The certificate fingerprint is published only with the first public release (SIGNER-PROTOCOL.md 2c). Until then "Fake Signer" stays **Partly** in SECURITY.md. |
| Independent human review | Community feedback once the code is public; a professional audit before real money. |
| Taps on partly covered screens | Fully covered taps are ignored; taps where only part of the window is covered aren't yet. |
| Task settings (`taskAffinity`) | Extra hardening against task-hijacking variants; Android 12+ already blocks the known ones. |
| Device-to-device transfer rules | Android 12+ may copy app data when moving to a new phone even with backup off. The wallet is useless there (it's locked to the old phone's Keystore), but an explicit rule would be cleaner. |
| Too many "Allow this app?" prompts | No limit yet on how often an app may ask; a "block this app" choice is planned. |
| Password when an allowed app's certificate changed | Today such an app is asked "Allow this app?" again; asking for the password too would be stricter. |
| Switching fingerprint off ignores some errors | If removing the fingerprint copy fails, it's not shown. |
| Copies of secrets in JavaScript memory | JavaScript text can't be wiped; byte arrays are. Moving signing into native code ("keep the key out of JS") is on the idea list. |
| StrongBox | Using the phone's separate security chip where available. |
| Fuzz testing in the automatic tests | The 500,000-case fuzzing was done once; it should become a repeatable test. |
| Clipboard | The Signer never copies secrets, but doesn't clear the clipboard either. |
| Dependency review | Must be repeated before each release (DEPENDENCIES.md). |
